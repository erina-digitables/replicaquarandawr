# Architecture: Dawr tracker (a rebuild of Quran Dawr's core features)

Inputs: `replica/recon.md`, `replica/features.csv`. Screen IDs (S01…) and flow IDs (F01…) refer to the recon map.

## Stack

No existing stack in the project, so the managed defaults apply.

| layer | choice | why |
| --- | --- | --- |
| web | Next.js (App Router) + TypeScript, server actions | one codebase for pages and mutations. Every screen is a server component plus small client islands (checklist taps, chart) |
| styling | Tailwind, tokens from replica-design | the original is a single mobile-first column of cards. Tailwind plus a token file covers light/dark cleanly |
| mobile | none at first. The web app is a PWA (installable, add to home screen) | the core loop is one tap per quarter, so a good PWA covers it. Expo can come later if push reminders need it |
| database | Postgres on Supabase | relational day/quarter data and SQL aggregates for stats. RLS gives per-user isolation for free |
| ORM | none: `supabase-js` + typed queries generated by `supabase gen types` | 3 tables plus a view. RLS needs the user's JWT on every query, which supabase-js already does |
| auth | Supabase Auth (email + password, recovery by OTP code or link, anonymous sign-in for the demo) | covers sign up, sign in, the RESET code flow (F08) and "Try demo" without custom crypto |
| payments | none for now | the PRO tier is `skip` in the matrix. Add Stripe Checkout if replica-entrepreneur prices a tier |
| email | Resend as Supabase Auth's custom SMTP | the built-in Supabase mailer is rate-limited and not for production. Resend handles reset emails and later reminders |
| jobs | Vercel Cron (one nightly job) | only needed to clean up stale demo users. Streaks are computed, not stored, so there's no midnight rollover job |
| files | none | the app stores no uploads |
| hosting | Vercel | zero-config Next.js, preview deploys, cron |

One database, one app, no services.

## Schema

Tables: 4 (`quarters` reference, `profiles`, `daily_logs`, `log_quarters`), plus 1 view (`day_summaries`) and 4 functions. Access rules: **Postgres row level security** on every table. The migrations live in [`web/supabase/migrations/`](../web/supabase/migrations) (moved there by replica-backend, which also added write functions, rate limits and a job log; see `backend.md`).

Decisions behind it:

- **240 quarters, not 120.** `quarters.rub` 1-240, with juz/hizb/rub-in-juz enforced by check constraints so the maths can't drift (this fixes the original's "4 Qtrs = 1 Juz = 0.5 Juz" contradiction). Seed it from public Quran metadata (Tanzil `quran-data`, with attribution) including juz names and start surah:ayah.
- **Rows, not arrays.** The original keeps `completed_quarters: string[]` on the day. We use one `log_quarters` row per quarter per day, which is where the quality rating, the "planned" flag and the timestamp live. Stats, "Top Juz" and search by juz become plain SQL.
- **A day is a `date` in the user's time zone** (`profiles.timezone`, an IANA name captured at sign-up). `unique (user_id, log_date)` makes one log per day a database rule. `primary key (log_id, rub)` stops the same quarter being logged twice on a day, so a double tap can't double-count.
- **Target snapshot.** `daily_logs.target_quarters` copies the target when the day is first touched, so changing the goal later doesn't rewrite past "Target Met" badges.
- **Streak is derived** (`current_streak()`): consecutive goal-met days ending today, or ending yesterday while today is still in progress, so it doesn't drop to 0 at breakfast.
- **Passwords never reach our tables.** They stay in `auth.users`, hashed. The account page shows no password (the original's reveal/copy is `skip`).
- **Username sign-in.** `email_for_username()` is `security definer` and revoked from `anon` and `authenticated`. Only the server (service role) calls it, so the browser can't enumerate usernames.
- On delete: `auth.users` → `profiles` → `daily_logs` → `log_quarters` all `cascade` (account deletion wipes everything). `quarters` is `restrict` (reference data is never deleted under live logs).

Checked locally against embedded Postgres (PGlite) with a stand-in for Supabase's `auth` schema. Passing:
- quarter maths constraints
- case-insensitive unique username
- one-quarter-per-day uniqueness
- the done/planned row constraints
- streak = 1 with yesterday met and today partial, and 2 once today is met
- RLS blocks a user writing or reading another user's rows, and blocks users from calling `email_for_username`
- full cascade on user delete

Not yet run on a real Supabase project.

## API

All mutations are Next.js **server actions** called with the user's session, so RLS applies. Reads happen in server components. The only route handlers are the auth callback and the cron.

### Auth (F01, F02, F08, F10)

| method path | does | who | input | output | flow |
| --- | --- | --- | --- | --- | --- |
| action `signUp` | create auth user; trigger creates the profile | anon | full_name, username, email, password, timezone (from `Intl`) | session → redirect `/today` | F01 |
| action `signIn` | if the identifier has no `@`, resolve it with `email_for_username` (service role), then `signInWithPassword` | anon | identifier, password | session, or one generic "wrong username or password" | F02 |
| action `startDemo` | anonymous sign-in, profile `is_demo`, seed 7 days of sample logs | anon | — | session → `/today` | F01 alt |
| action `requestPasswordReset` | `resetPasswordForEmail` (resolve username first). Always answers "if that account exists, we sent a code" | anon | identifier | ok | F08 |
| action `verifyResetCode` | `verifyOtp({ type: 'recovery' })` | anon | email, 6-digit code | recovery session → `/reset/new` | F08 |
| action `updatePassword` | `auth.updateUser({ password })` | recovery session or signed in | password | ok | F08 |
| GET `/auth/callback` | exchange code for a session (link-style reset, email confirm) | anon | `code` | redirect | F08 |
| action `signOut` | end session | user | — | redirect `/` | F10 |

### Today, plan, target (F03, F04, F05, F07)

| method path | does | who | input | output | flow |
| --- | --- | --- | --- | --- | --- |
| page `/today?date=YYYY-MM-DD` | loads the day: log, its quarters (planned + done), target, streak. With no plan, shows the suggested next N quarters | user | date (default: today in the user's time zone) | S04 | F03, F05 |
| action `setQuality` | upsert the day log (snapshot target), upsert `log_quarters` with quality + `completed_at` | user | date, rub, quality | updated day summary | F03 |
| action `uncheckQuarter` | clear quality; delete the row if it wasn't planned | user | date, rub | updated day summary | F03 |
| action `savePlan` | replace the planned set for the day | user | date, rub[] | day | F04 |
| action `lockPlan` / `unlockPlan` | toggle `plan_locked` (the checklist then shows only planned quarters) | user | date | day | F04 |
| action `updateTarget` | set `profiles.daily_target`. If today's log has no completed quarters yet, update its snapshot too | user | n (1-240) | profile | F07 |
| action `updateProfile` | name, username, timezone, theme | user | fields | profile | S08 |

Suggestion rule (no plan for the day): continue after the highest `rub` completed on the most recent logged day, wrapping 240 → 1, for `daily_target` quarters. Pure function, unit tested.

### Stats and history (F05, F06, F11)

| method path | does | who | input | output | flow |
| --- | --- | --- | --- | --- | --- |
| page `/stats?date=` | month and year totals, goal-met day count, week bars (Mon-Sun around the date), weekly total and average, streak | user | date | S06 | F05 |
| page `/history?filter=&q=&cursor=` | `day_summaries` newest first, filter all / met / incomplete, search by date or juz number, 30 per page | user | filter, q, cursor | S07 | F06 |
| action `deleteDay` | delete a day's log (cascades its quarters) | user | date | ok + undo token (row kept in memory for 5 s, client-side undo re-inserts it) | F06 |
| action `resetAllLogs` | delete all of the user's logs after a typed confirmation | user | confirm text "RESET" | ok | F11 |
| action `deleteAccount` | service role `auth.admin.deleteUser(uid)`, which cascades everything | user | confirm | redirect `/` | GDPR |

Webhooks in: none. Webhooks out: none.
Jobs: `purge-demo-users`, Vercel Cron daily at 03:00 UTC, deletes `is_demo` users older than 24 h.

## The parts that bite

- **Time zones and DST:** "today" is always `now() at time zone profiles.timezone`, worked out on the server, never from the client clock alone. Dates are stored as `date`, so DST never shifts a day. If a user's time zone changes, ask before switching (logs keep their dates).
- **Idempotency:** a double tap or retry of `setQuality` is an upsert on `(log_id, rub)` and lands once. The day log is `insert … on conflict (user_id, log_date)`.
- **Races:** two tabs tapping at once both upsert the same keys. Last write wins on quality, which is acceptable. The day row can't be duplicated (unique constraint).
- **Optimistic UI / offline:** the checklist updates instantly (`useOptimistic`) and rolls back on error with a toast. A real offline queue is a could-have, not in v1.
- **Rate limits:** sign-in, reset and username lookup go through Supabase Auth's limits. Add a per-IP limit (Vercel KV or Upstash) on `signIn` and `requestPasswordReset` because of the username→email step.
- **Email deliverability:** custom SMTP (Resend) with SPF/DKIM on our domain before launch. The default Supabase mailer is capped at a few per hour.
- **Search:** history search is a `where log_date::text like` or `juz = any(juz_touched)` filter over a few hundred rows per user. No search engine needed.
- **GDPR deletion:** a single cascade from `auth.users` covers it. No logs or analytics hold Quran-reading data outside the DB.
- **Multi-tenancy:** single-user data only. RLS on `auth.uid()` everywhere. Teacher/student sharing would add a `circles` table later.
- **Quran metadata licence:** the Tanzil metadata needs attribution in the footer/about. We store no Quran text.

## Build order

1. **Vertical slice:** sign up → today → tap a quarter → progress bar moves → reload and it's still there.
   - Screens: S02, S01, S04 (bare).
   - Tables: all four, with `quarters` seeded.
   - Routes: `signUp`, `signIn`, `signOut`, `/today`, `setQuality`, `uncheckQuarter`.
2. **Must-haves:**
   - Today: date navigation, goal card and banner, suggestion rule (S04).
   - Target stepper and presets (S08 Target Config, `updateTarget`).
   - Streak pill (`current_streak`).
   - History list (S07 basic, `day_summaries`).
   - Mobile-first layout plus the 375px header fix.
   - Username-or-email sign-in.
3. **Should-haves:**
   - Plan builder and lock (S05, `savePlan`, `lockPlan`).
   - Statistics with the week chart (S06).
   - History filter and delete with undo.
   - Account page (S08, no password shown).
   - Password reset by code or link (S03, F08).
   - Light/dark/system theme.
   - **Could-haves after that:** "Try demo" sandbox with cron purge, history search, reset all logs, revision tips, juz names and start ayah per quarter, toasts.
4. **Fixes from replica-entrepreneur:** slot reserved. Likely candidates from recon: a teacher view, reminders, offline queue, a quality heat-map over the 240 quarters ("which quarters keep needing work").
